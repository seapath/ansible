# Gating RBD-backed containers on Ceph readiness

How a quadlet container whose volume lives on a Ceph RBD image is kept from
starting before the cluster can serve it, why the wait sits inside
`seapath-rbd-mount`, and what was measured to decide that.

## The problem

A quadlet with an RBD-backed volume calls `seapath-rbd-mount` from
`ExecStartPre=` and orders itself after `network-online.target`. At boot the
Ceph cluster needs a minute or two beyond that point to form its quorum, so the
mount helper runs against an unreachable cluster and fails. The container then
sits failed on a host that is otherwise healthy.

The missing piece is a dependency on "the pool can be served", which no
existing unit expresses.

## Ordering alternatives that do not work

These were considered first because they would have cost nothing to write.

### `After=rbdmap.service`

`rbdmap.service` ships with `ceph-common` and is present on SEAPATH machines
(it is in the cukinia systemd allowlist). It runs `rbdmap map` over
`/etc/ceph/rbdmap`, which holds only comments here: zero lines, exit 0
immediately. The unit is itself only `After=network-online.target`, so ordering
behind it places a container at the same instant it already starts at.

Filling `/etc/ceph/rbdmap` for real does not help either. `rbdmap` only maps.
It does not create the image on first use, does not `mkfs`, does not mount. It
is boot-wide static configuration, so the mount stops being tied to the
container lifecycle and `ExecStopPost=` loses its meaning. And on failure it
makes one pass and gives up, leaving the unit failed for good.

### `After=remote-fs.target`

`remote-fs.target` is a passive synchronisation point: ordering behind it pulls
nothing in, and on a host with no network mount it is reached in milliseconds.

On a cluster node it would work by accident. The CephFS mount installed by
`deploy_cephfs` is `_netdev`, hence a member of `remote-fs.target`, and it
carries `x-systemd.requires=ceph-mds-ready@seapathcephfs.service`, which waits
for an active MDS and therefore for quorum. Relying on that has two problems.
`deploy_cephfs` is optional (`when: deploy_cephfs is defined and deploy_cephfs
| bool`), so on a cluster deployed without CephFS the target has no member that
waits for Ceph and the gate silently disappears. And the coupling runs both
ways: the CephFS mount is required by the target, so its failure would take
down a container that does not use it.

### `ceph.target`

It means "the local Ceph daemons were started", which says nothing about
quorum, and it does not exist at all on a node running no local Ceph daemon.

## How VMs solve the same problem, and why containers cannot copy them

Worth stating, because it explains why this problem is new.

A VM disk is always a libvirt network disk (`<source protocol="rbd"
name="rbd/system_<vm>">`) generated by `vm_manager`, so QEMU talks to Ceph
through librbd in user space when it opens the disk. There is no `rbd map`, no
mount, and nothing to order in systemd.

VMs are started by Pacemaker, and the SEAPATH `VirtualDomain` resource agent
serialises on Ceph by itself: its `restore_config` reads the domain XML out of
the RBD image metadata, so without a quorum the resource cannot even be
defined. Pacemaker then retries without a rate limit, which is what systemd
declines to do after `StartLimitBurst`.

## The two designs that do work

### Option A: the wait inside `seapath-rbd-mount` (adopted)

The helper already runs at exactly the right moment and already needs the
cluster, so the wait is a precondition of its own work. The obstacle is
`TimeoutStartSec`, which covers the whole start-up including `ExecStartPre=`
and defaults to 90 s, so a 300 s loop would be killed. `EXTEND_TIMEOUT_USEC`
sent to systemd from inside the loop pushes that deadline back.

A quadlet author writes `ExecStartPre=` and `ExecStopPost=`, and nothing in
`[Unit]`.

### Option B: `rbd-map@.service` plus a `.mount` unit per image

Quadlet derives `RequiresMountsFor=` from every host path in `Volume=`, so a
`.mount` unit at that path is pulled in and waited for with no plumbing in the
`.container` file at all. The mount unit `Requires=` an
`rbd-map@<image>.service` that does the wait, the create, the map and the
`mkfs`, and unmaps in its `ExecStop=`.

## What was measured

On elabo1 (Debian 13, podman 5.4.2, systemd 257). Both designs depend on
generator behaviour that is worth checking rather than assuming.

A test quadlet declaring only `Volume=/mnt/rbd/testimg:/data:rw` and an
`ExecStartPre=` generates:

```
[Unit]
RequiresMountsFor=/mnt/rbd/testimg     <- derived from Volume=
[Service]
Type=notify
NotifyAccess=all
```

so both designs are available. Then, with `TimeoutStartSec=20` and an
`ExecStartPre=` that waits 40 s:

| Unit | Notification | Outcome |
|---|---|---|
| control | none | killed at 20 s, `Result=timeout` |
| test | `EXTEND_TIMEOUT_USEC` every second | `active`, `Result=success` at 40 s |

The full option B chain was built and behaves as designed, waiting on the
simulated map before mounting and before starting the container:

```
Starting rbd-map@testimg.service...   waiting for ceph...   (15 s)
Finished rbd-map@testimg.service
Mounting mnt-rbd-testimg.mount... Mounted
Starting zz-gatetest-mnt.service... Started
```

Option B also fails better. When the gate fails, the container job is cancelled
as a dependency failure with `NRestarts=0`, so `Restart=` is never entered and
`StartLimitBurst` is never touched:

```
Failed to start rbd-map@testimg.service
Dependency failed for zz-gatetest-mnt.service
Job zz-gatetest-mnt.service/start failed with result 'dependency'
```

Teardown needs `StopWhenUnneeded=yes` on the `rbd-map@` unit as well as on the
`.mount`. With it on both, stopping the container unmounts and then unmaps on
its own. With it only on the mount, the unmap never runs.

## Why option A was chosen

Option B is cleaner inside the `.container` file and heavier everywhere else.
Counting only the lines it removes from the quadlet flatters it; what matters
is the total work of adding one RBD-backed container.

| | Option A | Option B |
|---|---|---|
| Files to write per new container | 1 (`foo.container`) | 2 to 3 |
| Files shipped by the role | 2 scripts | 1 templated unit + 1 `.mount` per image |
| Image name and size | arguments of `ExecStartPre=`, one place | name in the unit file name, size has nowhere to go |
| Unmap on stop | `ExecStopPost=`, which can be forgotten | automatic |
| Ceph never answers | container retries every ~300 s until it succeeds | job cancelled, gate unit failed with the reason |
| Silent failure mode | `NOTIFY_SOCKET` absent: wait capped, logged once | escaped unit name wrong: systemd falls back to the parent mount and the gate does nothing, with no error |

Two warts sink option B at the current scale. Systemd requires the mount unit
to be named after the escaped path, and the hyphen is reserved, so
`/mnt/rbd/foo-data` needs a file called `mnt-rbd-foo\x2ddata.mount`, with a
literal backslash, generated through `systemd-escape -p`. Getting it wrong
produces no error at all. And a systemd template takes a single parameter,
already spent on the image name, so the size used to create the image on first
use has to move into a hardcoded default or a third file per image.

Option B becomes the better trade the day several RBD-backed quadlets are
written outside this repository, where automatic unmapping and a failure
attributed to Ceph are worth the extra files.

## Consequences to keep in mind

- **The deadline stays bounded.** Extending it forever would leave the unit in
  `activating (start-pre)` indefinitely, never failed, so nothing would ever
  alert. Failing at 300 s and letting `Restart=` retry is the deliberate
  choice.
- **The rate limit is not a concern here.** `StartLimitBurst` counts 5 starts
  in a 10 s window; attempts spaced by the 300 s deadline never approach it.
  The container recovers on its own, within 300 s of the cluster coming up.
- **A refused `systemd-notify` degrades the wait.** It is expected when the
  helper is run by hand. The wait then falls back to whatever timeout the
  caller imposes, and the helper says so once in the journal rather than
  swallowing it.
