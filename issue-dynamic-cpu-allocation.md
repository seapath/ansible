# RFC: dynamic allocation of isolated CPU cores

## 1. Context

On a SEAPATH node, real time is the product. A set of logical cores is removed
from the Linux scheduler at boot (`isolcpus=`) and reserved for latency
sensitive work. Everything else (OS, daemons, Ansible, Ceph, Cockpit) runs on
the remaining *housekeeping* cores.

Four kinds of actors compete for that isolated pool:

1. **VMs** (QEMU/KVM via libvirt): vCPU threads, emulator thread, vhost kernel
   threads, optional iothreads.
2. **Containers** (Podman, orchestrated by systemd quadlets).
3. **NIC IRQ threads**, pinned to isolated cores to keep network latency low.
4. **Operator tools** run ad hoc: a Sampled Values generator, a sniffer, a
   capture tool during commissioning.

These four actors are configured by four unrelated mechanisms, and none of them
knows about the other three. That is the root of the problem described below.

## 2. The problem

### 2.1 The placement decision is taken at the wrong time

Today a VM's affinity is frozen in the libvirt domain XML, generated by Ansible
from the inventory:

```yaml
cpuset: [4, 6]        # vCPU cores
emulatorpin: 8        # QEMU emulator thread
rt_priority: 90
```

```xml
<cputune>
  <vcpupin vcpu="0" cpuset="4"/>
  <vcpupin vcpu="1" cpuset="6"/>
  <emulatorpin cpuset="8"/>
</cputune>
```

Containers have the same pattern in the unit file (`CPUAffinity=`,
`CPUSchedulingPolicy=`), and NIC IRQs in `/etc/nic-irq-affinity.conf`.

The core numbers are chosen by a human, at deployment time, from a spreadsheet
view of the node. But the only moment at which the right answer is knowable is
**when the workload actually starts, on the actual node**: that is when the
node's topology and the real occupancy of the pool are both known.

### 2.2 Static pinning and live migration are incompatible

This is the blocking one for cluster mode. If a VM's XML says "cores 4 and 6",
then cores 4 and 6 must be kept free **on every node the VM could land on**.
With N migratable VMs on a 3 node cluster, the operator has to hand-solve a
global placement problem, and keep solving it every time a VM is added, resized
or removed.

Two consequences we hit in practice:

- **Conflicts.** Two VMs designed independently both ask for cores 4 and 6.
  They coexist happily until Pacemaker puts them on the same node after a
  failure, and then they silently share cores. Nothing detects it.
- **Waste.** To avoid the above, cores are reserved defensively on all nodes for
  VMs that are not running there. Isolated cores are the scarcest resource on
  the machine, and a large fraction of them are idle by construction.

### 2.3 No shared view of the pool

There is no place where "who owns which isolated core" is answerable. The VM
inventory, the quadlet units, the IRQ configuration file and whatever the
operator typed in a terminal live in four separate worlds. So:

- an operator launching an SV generator has no way to know which cores are
  taken, and pins by hand with `taskset` and `chrt`;
- a container deployed later can legitimately be given a core that a VM already
  uses;
- overlaps are not errors anywhere, they are just latency, discovered later
  during a cyclictest campaign or, worse, in production.

### 2.4 Failures are silent, and silently lose real time

When the intended placement cannot be honoured (core taken, pool exhausted,
node with a different topology than expected), nothing fails loudly. The
workload runs. It just no longer has the RT guarantees it was designed for.
For a protection function, "running without its latency guarantee" is exactly
the state we must never be unable to see.

### 2.5 Hyper-Threading is not modelled

Two logical siblings share the execution resources of one physical core. Two
independent RT threads placed on a sibling pair interfere. Sometimes we want a
whole physical core for one thread (sibling left idle), sometimes we do not.
A flat list of core numbers in the inventory cannot express that intent, so the
distinction is carried informally by conventions and comments.

### 2.6 Exclusivity is the only available answer

The current model has one implicit isolation level: this core is mine. That is
right for an RT vCPU, and wasteful for everything else. A NIC IRQ thread, a
QEMU emulator thread or a low duty SV consumer each burn a full isolated core
while using a few percent of it. Worse, since they are alone on their core,
their RT priorities never arbitrate against anything: priority becomes
decorative. There is no way to say "these three low duty actors can share one
core, and here is the priority order between them".

## 3. What a solution has to respect

Constraints coming from the domain, not negotiable:

- **Never prevent a workload from starting.** A pinning problem must degrade the
  workload, not deny service. A protection VM running degraded is bad; a
  protection VM that did not start is an outage.
- **No new single point of failure**, no new boot ordering dependency, no
  component whose crash leaves the node in an undefined state.
- **Playbooks re-run on live substations.** The mechanism must tolerate being
  re-applied, and must recover on its own from crashes, kills and reboots
  without a cleanup procedure.
- **Zero per-node configuration in the workload definition.** A VM definition
  must be node agnostic, otherwise migration is back to square one.
- **Everything observable.** Any deviation from the requested placement must be
  visible in monitoring, with enough context to know what lost what.

## 4. Proposed approach

The single idea: **replace static placement decisions by a declaration of
intent, and resolve that intent at launch time against the live state of the
node.** An actor says "I need one isolated core, FIFO 90, alone on its physical
core"; the node decides which core that is, at the moment it starts.

Below are the concepts this requires, and why each one is shaped that way.

### 4.1 Declare intent, not core numbers

The inventory stops naming cores and names **isolation levels**:

| Level | Meaning |
|---|---|
| `none` | housekeeping, the Linux scheduler decides |
| `exclusive_logical` | one dedicated isolated logical core |
| `exclusive_physical` | one whole physical core, HT sibling kept idle |

Why: this is the actual engineering requirement, and it is the part that is
stable across nodes and over time. "Core 6" is an implementation detail of one
node on one day. Making the intent explicit also makes HT a first class notion
(2.5) instead of a convention, and makes it possible to audit a fleet by asking
what each VM *asked for*, not what it happened to get.

### 4.2 Resolve at start and at migration arrival

The resolution point for a VM is a **libvirt hook**, which libvirt calls on
every VM lifecycle event. It runs on the destination node, at start and at
incoming live migration, when the node's topology and occupancy are known.

Why a hook and not the XML: it is the only place where a per node, per instant
decision can be taken. It also gets migration for free: arriving on a new node
is just another allocation round on that node's pool.

The hook must **always exit 0**. A non zero exit aborts the VM. This directly
encodes the "never prevent a workload from starting" constraint.

### 4.3 The profile travels with the workload

For VMs, the intent is stored as **Ceph RBD image metadata** on the VM's disk,
not in the node's configuration.

Why: the disk is the one thing that follows the VM everywhere in a cluster.
Wherever the VM lands, the profile is there, and the local node resolves it
against its own topology. No per node configuration to synchronise, which is
what makes 2.2 go away rather than move somewhere else.

This does not add an authoring surface: the inventory stays the place where
everything is written, exactly as today. Quadlets are pushed from the inventory
by Ansible, and VM profiles would be pushed by `vm_manager`, which already owns
RBD metadata and is therefore the natural place to write the profile at VM
creation and propagate it on clone. RBD is where a VM's allocation intent
*lives and travels*, not where it is authored.

**The carrier is per mode, the mechanism is not.** RBD is the cluster carrier,
chosen because migration is what makes a travelling profile necessary. A
standalone VM's disk is local and carries nothing, so its profile is written to
a file on the host (`/etc/seapath/alloc.d/<vm>.yaml`) by the same Ansible run,
from the same inventory variable. The hook looks in RBD first, then in the file:
a leftover local file cannot override a profile that is meant to travel.

This is worth doing rather than declaring dynamic pinning cluster-only, because
a profile expresses things a static `<cputune>` cannot: the placement and
priority of **vhost threads**, colocation through slots, and any priority
relation with a NIC IRQ, a container or an operator tool, none of which a domain
XML can see.

The vhost case is the sharpest one, and it is not that libvirt cannot reach
those threads: `<emulatorpin>` does, but it reaches them *together with the
emulator thread*, as one core set for both. There is likewise no vhost
counterpart to `<emulatorsched>`, so their scheduling policy and priority cannot
be stated apart from the emulator's either. That is a single decision covering
two workloads with opposite needs. The vhost threads carry the guest's SV and
GOOSE traffic and want FIFO; the emulator thread does housekeeping work and
should stay SCHED_OTHER, ideally not on an isolated core at all. Even the
minimal split, vhost in FIFO and emulator in SCHED_OTHER while both stay on the
same cores, is already out of reach of `<cputune>` and needs a hook. Once a hook
is in the picture, letting the two land on different cores as well costs nothing
more, and that is what makes it worth doing properly rather than working around
`<emulatorpin>`.

The alternative would be a second mechanism doing the same job for standalone,
which is strictly more work than a second carrier.

### 4.4 The pool state is derived from the kernel, not stored

The central question of any allocator is "what is already taken". The answer
here is **read from the kernel at every request**: thread affinities from
`/proc`, IRQ affinities from `/proc/irq`, topology from `/sys`. A thread counts
as occupying isolated cores only if its affinity mask is a subset of the
isolated set, so unpinned threads do not pollute the accounting.

Why not a database or a daemon:

- A database goes stale. A VM crashes, a hook is interrupted, a node reboots,
  and the recorded state no longer matches reality. Then you need a
  reconciliation loop, and a way to decide who is right.
- Live rediscovery is **self healing by construction**: when a VM dies, its
  threads leave `/proc` and its cores are free again on the next read. No
  release protocol, no cleanup, no orphan state.
- A daemon adds a boot dependency, a crash surface and a restart protocol on
  every upgrade, on a machine whose whole point is predictability.

The kernel is the source of truth, and it is never wrong about itself.

### 4.5 Serialisation by a kernel primitive

Concurrent allocations (two VMs migrating in at the same time, a container
starting while a VM boots) are serialised by an **exclusive `flock`** on a file
in `/run`, held across the discover, allocate and apply window.

Why: once the pinning is applied, the next caller sees it in `/proc` and will
not hand out the same core. That closes the race with no lock manager, no IPC
and no arbitration service. `/run` is tmpfs, so no stale lock survives a
reboot. A kernel primitive cannot crash on us.

### 4.6 Claims for the actors the kernel cannot attribute

QEMU threads are discoverable from `/proc`, containers and third party
processes are not identifiable that way. They register a **claim** (label, PID,
cores) in a small runtime file, which the pool reads alongside the kernel
sources. A claim whose PID is gone is dropped on the next read.

Why: it keeps the self healing property of 4.4 for actors that need an explicit
registration, using process liveness (a kernel fact) rather than a release
protocol that a crash can skip. NIC IRQs deliberately do not use this: they
have no PID and the kernel already exposes their affinity, so they are simply
read passively.

### 4.7 Degrade in a documented order, and record it

When the requested level cannot be satisfied, the allocator walks a fixed
ladder rather than failing:

`exclusive_physical` then `exclusive_logical` (RT isolation kept, HT noise
possible) then housekeeping (RT isolation lost).

The two outcomes are **not** the same severity and must not be reported the
same way: losing an idle HT sibling is a performance concern, losing isolation
means the actor no longer has a real time guarantee. Every degradation is
logged and exported with its severity and its context.

Why: this is the direct answer to 2.4. The system is allowed to give you less
than you asked for, and it is never allowed to do so quietly.

### 4.8 Placement strategies are a node level policy

How free cores are picked matters as much as which are picked, because of HT.
The node exposes a strategy: spread one thread per physical core (best HT
isolation), pack siblings first (density), or repack, which compacts existing
threads to free a whole physical pair before an `exclusive_physical` request
falls back.

Why make it a policy instead of hardcoding one: the tradeoff between density
and HT quietness is a site decision, not a platform decision. Repacking in
particular is what lets a fragmented pool still honour a strict request, which
is the common case on a node that has been running for months.

### 4.9 Named shared core slots for controlled colocation

To answer 2.6, an object is needed between the actor and the core: a **slot**,
a named group of isolated cores that several actors share, each keeping its own
scheduling policy and priority.

The point is not only density. Once several actors are on the same core, their
RT priorities finally arbitrate against each other, which is the actual
mechanism we want for "the IRQ thread always wins over the consumer that reads
its packets". Exclusivity cannot express that relation at all.

Two design rules make it usable in a cluster:

- **The name is the whole coordination mechanism.** Slot names are host global
  and resolved locally: `slot: sv0` in a VM profile means "this node's sv0",
  whichever node the VM lands on. This is what keeps workload definitions node
  agnostic (4.3) while still allowing them to target something node specific.
- **The fixed actor publishes its position, mobile actors join it by name.**
  A NIC IRQ is physically bound to the machine and its core is an operator
  decision from the inventory; it has no placement problem to solve at runtime,
  so it declares its slot. VMs, containers and tools move between nodes, so
  their cores must be allocated from the pool at first reference. Never the
  reverse: asking the pool for a placement that can never be released would be
  a static assignment in disguise, with an availability dependency for no gain.

Colocation can be dangerous (sharing a core with an RT vCPU can stall a guest
kernel). The choice here is to **warn, never refuse**: the operator is the
authority on their own machine, and a mechanism that can refuse is a mechanism
that can prevent a VM from starting. Risky patterns are detected and exported
as metrics instead.

### 4.10 Observability is part of the feature, not an add on

Because placement is now dynamic, "which core is this VM on" stops being
answerable by reading the inventory. So the system must answer it itself: pool
occupancy per actor, current degradations with their severity, and risky
colocations, exported through the existing node_exporter textfile path so the
collection infrastructure does not change.

Why it is not optional: dynamic allocation trades a decision the operator used
to make by hand for a decision the node makes. That trade is only acceptable if
the operator can see the outcome at least as clearly as before.

Concretely: a Grafana dashboard showing who holds which core, plus alerting
rules for pool exhaustion and degradation. The rules would be provided as
documentation, for the operator to paste into their own Prometheus
configuration, rather than shipped as deployed configuration: the supervision
stack is site owned and is not managed by this repo.

## 5. What this adds, and what keeps working

This is an **additional way of doing things, not a replacement**. Nothing that
works today stops working, and adoption is per workload.

| Today | With seapath-alloc |
|---|---|
| `cpuset` / `emulatorpin` / `rt_priority` in the VM inventory | isolation intent in the VM profile, cores chosen at start |
| `CPUAffinity=` in quadlet units | pin helper in `ExecStartPost=`, cores from the pool |
| manual `taskset` / `chrt` by the operator | wrapper that claims cores, then execs the tool |
| static NIC IRQ affinity | unchanged, plus optional slot declaration so others can join |

The left column keeps working, by construction:

- **A VM with no profile is not touched.** The hook resolves it to an all `none`
  profile, which means no `taskset` and no `chrt` at all. A VM statically pinned
  by its libvirt `<cputune>` keeps exactly the placement its XML gave it.
- **Statically pinned VMs are still accounted for.** The pool derives occupancy
  from `/proc` for every QEMU thread, whoever pinned it. So a VM pinned by XML
  makes its cores unavailable to dynamically allocated actors, with no
  registration and no configuration. The two mechanisms do not fight, because
  the dynamic one observes the static one.
- NIC IRQ configuration deliberately does not change: it is already correct for
  a fixed actor. It only becomes visible to the allocator.

That is what makes this landable on an existing fleet: nothing moves when the
mechanism is deployed, and workloads opt in one at a time, by being given a
profile.

The proposal is additive from end to end, and the VM XML templates need no
change. They already support both modes, because everything
inside their `<cputune>` block is conditional on `cpuset` being defined, and the
vCPU count already falls back to `nb_cpu` when it is not. A VM that adopts a
profile simply stops setting `cpuset`, and renders the empty `<cputune>` that
every non-RT VM already renders today. A VM that keeps `cpuset` keeps its static
pinning, forever if that is what suits it.

The one thing not to do is set both on the same VM: libvirt would apply the XML
at start and the hook would re-pin afterwards. Pick one per VM.

## 6. Out of scope

- NUMA awareness: SEAPATH targets single socket servers today.
- Changing a running workload's profile without a restart.
- Any "notify me when a core frees up" mechanism: no use case identified.
- Cluster wide placement (deciding which node a VM should run on): that stays
  Pacemaker's job. This proposal is strictly per node.

## 7. Delivery: one reviewable step at a time

The work is cut into independent steps, each proposed as its own pull request.
Every step should be self-contained: the modules it adds import cleanly and come
with their own tests, so the series stays bisectable and a reviewer can run what
they are reading.

| # | Step | What it adds |
|---|---|---|
| 1 | CPU topology reader and live core pool | `/sys` topology, live occupancy from `/proc`, passive NIC IRQ reading, `flock` serialisation |
| 2 | Allocation engine and HT repacker | pure logic: intent plus free cores gives placement, the degradation ladder, the three strategies |
| 3 | QEMU thread discovery and pinning application | thread classification, apply order vCPUs then emulator then vhost then iothreads |
| 4 | libvirt hook and the Ansible role | the full VM path, profile from RBD metadata, the deployable role |
| 5 | Claims registry, operator CLI, `seapath-run` | non-QEMU actors join the pool, pool state becomes inspectable |
| 6 | Container pinning for systemd quadlets | cgroup-level enforcement for multi-process services |
| 7 | Prometheus exporter and Grafana dashboards | pool and degradation metrics through the node_exporter textfile path |
| 8 | Named shared-core slots | controlled colocation and priority arbitration (section 4.9) |
| 9 | Pinning profile support in `vm_manager` | profile written at VM creation, propagated on clone |
| 10 | Local profile file for standalone VMs | second carrier, so standalone RT VMs are not restricted to what `<cputune>` can express |

Steps 1 to 3 are library only and change no behaviour on a deployed node: they
can be reviewed as one PR if a series of three is not worth the overhead. Step 4
is the first one that does something. Steps 5 to 10 each stand alone and can
land in any order after 4, except 8 which builds on 5 and 6. Steps 9 and 10 are
the two carriers and are independent of each other.

No step in the series removes or rewrites an existing mechanism, so each one can
be merged, or refused, without holding up the others and without a migration on
any deployed machine.

## 8. Points to discuss

**Default allocation strategy for the fleet.** `spreading` is the conservative
default: one thread per physical core, best HT quietness, but it fragments the
pool over time and a long lived node can end up unable to honour an
`exclusive_physical` request while holding plenty of half used pairs.
`repacking` keeps strict requests satisfiable by compacting first, at the cost
of moving threads that already belong to running workloads. Which one should be
the shipped default, and is moving an existing RT thread acceptable on a live
substation?
